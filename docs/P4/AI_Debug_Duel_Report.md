# AI 调试对决实验报告


## 1. 实验目标

本实验选择系统集成过程中较有代表性的 3 个技术性 Bug，比较纯人工调试与 AI 辅助调试的差异，分析 AI 在代码定位、根因判断、修复方案生成中的价值与局限。

本次 Bug 覆盖以下关键模块：

1. 订单状态流转与权限校验；
2. 消息会话与未读数一致性；
3. 智能匹配结果落库与规则追踪。


---

## 2. Bug #1：订单状态流转缺少权限与状态前置校验

### 2.1 问题描述

在需求/订单模块集成早期，订单状态流转接口存在潜在风险：

- 非接单用户可能提交订单；
- 非发布者可能确认完成；
- 任务尚未提交时可能被确认完成；
- 已接单任务可能被重复接单。

该问题会破坏 P4 要求中的完整业务流程“发布需求 -> 另一用户接单 -> 完成 -> 评价”，导致订单状态与用户身份不一致。

### 2.2 纯人工调试过程

| 步骤 | 人工调试记录 |
|---|---|
| 问题描述 | 测试完整流程时，重点检查订单接口是否只依赖订单 id，而忽略当前 token 对应用户身份。 |
| 定位方法 | 人工阅读 `OrderController` 中 `/claim/{id}`、`/submit/{id}`、`/confirm/{id}` 接口逻辑，结合订单表字段 `user_id`、`taker_id`、`status`、`is_claimed`、`is_completed` 推断状态机。 |
| 定位耗时 | 约 35 分钟。 |
| 根因判断 | 订单接口不仅要更新状态，还必须同时校验“当前用户身份”和“当前订单状态”。如果只按订单 id 更新状态，会造成越权操作或非法状态跳转。 |
| 人工修复思路 | 增加状态机约束：接单前判断未被接取；提交前判断当前用户是接取人；确认前判断当前用户是发布人且状态为 `SUBMITTED`。 |

### 2.3 AI 辅助调试过程

| 步骤 | AI 辅助调试记录 |
|---|---|
| 输入给 AI 的上下文 | `OrderController` 代码、订单表字段、期望流程“发布 -> 接单 -> 提交 -> 确认完成”、异常测试需求。 |
| AI 定位耗时 | 约 8 分钟。 |
| AI 定位是否准确 | 准确。AI 明确指出订单接口需要同时校验角色权限与状态前置条件。 |
| AI 修复方案 | 建议将订单状态流转作为状态机处理，并增加重复接单、非接取人提交、非发布人确认、未提交不能确认等判断。 |
| 方案质量 | 可用，但 AI 初版建议偏抽象，需要人工结合当前项目已有字段决定具体判断条件。 |

### 2.4 最终修复方案

最终代码采用以下方式修复：

- 创建订单时设置初始状态：`NEW`、`isClaimed = 0`、`isCompleted = 0`；
- 接单时检查任务是否存在、是否已被接取，成功后设置 `takerId`、`isClaimed = 1`、`status = IN_PROGRESS`；
- 提交时检查当前用户是否为 `takerId`，并检查任务是否已完成，成功后设置 `status = SUBMITTED`；
- 确认完成时检查当前用户是否为发布者、任务是否已提交、是否已确认完成，成功后设置 `status = COMPLETED`、`isCompleted = 1`。

### 2.5 验证结果

新增或完善以下测试：

- `OrderApiIntegrationTest`：覆盖发布任务、查询任务、接单、重复接单、非接取人提交、接取人提交、非发布人确认、发布人确认完成；
- `FullBusinessFlowIntegrationTest`：覆盖完整正常流程“注册 -> 登录 -> 发布需求 -> 接单 -> 完成 -> 评价”。

最终 Maven 测试结果：

```text

```

## 3. Bug #2：消息会话首次发送时未读数与会话状态不一致

### 3.1 问题描述

消息模块在首次发送消息时，需要自动创建会话并写入消息记录。早期实现容易出现以下问题：

- 首次创建会话时 `unreadCount` 为空，后续执行 `unreadCount + 1` 可能触发空指针；
- 消息写入成功但会话更新失败，造成消息存在但会话列表不更新；
- 读取会话消息后，消息已读状态与会话未读数未同步清零；
- 长消息直接写入 `lastMessage` 可能导致会话摘要过长。

### 3.2 纯人工调试过程

| 步骤 | 人工调试记录 |
|---|---|
| 问题描述 | 测试“用户 A 给用户 B 首次发消息 -> 用户 B 查询会话和未读数”时，关注会话表和消息表是否同步更新。 |
| 定位方法 | 人工检查 `MessageServiceImpl.sendMessage`、`getMessages`，对照 `message` 与 `conversation` 表字段。 |
| 定位耗时 | 约 30 分钟。 |
| 根因判断 | 消息发送不是单表操作，而是“查找/创建会话 -> 插入消息 -> 更新会话摘要和未读数”的组合操作，需要事务和空值保护。 |
| 人工修复思路 | 使用事务包裹消息发送；首次创建会话后允许 `unreadCount` 为空但更新时做 null-safe 处理；读取消息时清除当前会话未读数。 |

### 3.3 AI 辅助调试过程

| 步骤 | AI 辅助调试记录 |
|---|---|
| 输入给 AI 的上下文 | `MessageServiceImpl`、`Conversation` 实体、消息发送流程、异常现象“首次会话/未读数异常”。 |
| AI 定位耗时 | 约 6 分钟。 |
| AI 定位是否准确 | 准确。AI 指出这是会话聚合状态一致性问题，不应只检查 `message` 插入。 |
| AI 修复方案 | 建议为 `sendMessage` 添加事务；对 `unreadCount` 做空值保护；读取消息时同步清除未读数；限制 `lastMessage` 长度。 |
| 方案质量 | 基本可用。人工进一步确认了项目当前 `conversation` 表字段和 Mapper 方法后采纳。 |

### 3.4 最终修复方案

最终代码中：

- `sendMessage` 使用 `@Transactional(rollbackFor = Exception.class)`；
- 查找不到会话时自动创建 `Conversation`；
- 插入 `Message` 后更新 `Conversation.lastMessage`、`lastTime`、`unreadCount`；
- 对 `unreadCount` 使用空值保护：`conversation.getUnreadCount() == null ? 0 : conversation.getUnreadCount()`；
- 读取会话消息后调用 `markAsRead`，并将会话未读数清零；
- 会话摘要 `lastMessage` 截断到 100 字符以内。

### 3.5 验证结果

通过 `MessageApiIntegrationTest` 验证：

- 发送消息成功；
- 查询未读数成功；
- 查询会话列表成功；
- 查询会话消息成功；
- 给自己发消息失败；
- 空消息发送失败；
- 不带 token 访问失败。

最终 Maven 测试结果：

```text
Tests run: 37, Failures: 0, Errors: 0, Skipped: 0
```

## 4. Bug #3：智能匹配结果无法追踪命中的规则，旧匹配结果未清理

### 4.1 问题描述

智能匹配模块需要根据启用规则为候选用户打分，并保存匹配结果。早期算法设计中存在两个潜在问题：

- 匹配结果只保存 `userId`、`targetUserId`、`matchScore`，没有记录命中的规则 id，导致后续无法解释“为什么匹配”；
- 用户重新执行匹配时，如果不清理旧结果，`match_result` 中可能出现同一用户的过期匹配数据。

这会影响智能匹配的可解释性和结果一致性。

### 4.2 纯人工调试过程

| 步骤 | 人工调试记录 |
|---|---|
| 问题描述 | 前端展示匹配结果时，只能看到目标用户和分数，无法判断由哪条规则触发；重复执行匹配后可能出现历史结果残留。 |
| 定位方法 | 检查 `MatchEngine.execute` 生成 `MatchResult` 的字段，以及 `MatchServiceImpl.executeMatch` 保存结果前后的数据库操作。 |
| 定位耗时 | 约 40 分钟。 |
| 根因判断 | 匹配算法缺少“最佳命中规则”的追踪；服务层保存新结果前应先清理当前用户旧结果。 |
| 人工修复思路 | 在算法层记录最高分规则 `bestRuleId`；在服务层执行匹配前调用 `deleteByUserId(userId)`。 |

### 4.3 AI 辅助调试过程

| 步骤 | AI 辅助调试记录 |
|---|---|
| 输入给 AI 的上下文 | `MatchEngine`、`MatchResult`、`MatchRule`、`MatchServiceImpl`，以及需求“结果可解释、重复执行不保留旧结果”。 |
| AI 定位耗时 | 约 10 分钟。 |
| AI 定位是否准确 | 基本准确。AI 指出需要在结果中记录规则 id，并在重新匹配前删除旧结果。 |
| AI 修复方案 | 在循环规则时维护 `bestRuleId` 和 `bestRuleScore`；保存结果前清空该用户旧记录。 |
| 方案质量 | 可用。人工补充了 TopN 排序和无候选用户返回空列表的边界处理。 |

### 4.4 最终修复方案

最终代码中：

- `MatchEngine.execute` 对每个候选用户累计规则分数；
- 记录分数最高的规则 `bestRuleId`，并写入 `MatchResult.ruleId`；
- 结果按 `matchScore` 降序排序并限制 TopN；
- `MatchServiceImpl.executeMatch` 在插入新结果前删除当前用户旧匹配结果；
- 无启用规则时抛出明确异常；无候选用户时返回空列表。

### 4.5 验证结果

通过 `MatchEngineTest` 验证：

- 按信用规则返回匹配用户；
- 匹配结果按分数降序排列；
- TopN 限制生效；
- 没有候选用户或没有命中规则时返回空列表。

最终 Maven 测试结果：

```text
Tests run: 37, Failures: 0, Errors: 0, Skipped: 0
```

## 6. 分析结论

### 6.1 AI 表现较好的 Bug 类型

AI 在以下类型问题中表现较好：

1. **状态机类问题**：例如订单从 `NEW` 到 `IN_PROGRESS`、`SUBMITTED`、`COMPLETED` 的流转约束；
2. **事务一致性问题**：例如消息发送同时涉及会话和消息两张表；
3. **数据可解释性问题**：例如匹配结果需要保留命中规则 id；
4. **测试用例补全**：AI 能较快提醒需要覆盖重复接单、越权提交、空消息、自发消息等异常路径。

### 6.2 AI 表现较差或需要人工把关的地方

1. AI 容易给出抽象建议，但不一定完全符合当前实体字段和数据库表结构；
2. AI 初版方案有时只关注后端逻辑，忽略前端字段命名和接口返回格式；
3. AI 可能建议“重构为完整状态机类”，但在课程项目时间有限时，人工需要判断是否采用轻量级修复；
4. AI 不能替代人工确认最终业务规则，例如“订单是否允许发布者取消”“评价是否必须在确认完成后才能提交”等。

### 6.3 是否出现只修表象、不找根因

出现过这种风险。例如订单接口异常时，如果只在前端隐藏按钮，表面上普通用户无法点击“确认完成”，但接口仍可能被直接调用。因此最终修复没有只依赖前端控制，而是在后端接口中加入了身份和状态校验。

### 6.4 哪些上下文能显著提升 AI 调试质量

以下上下文最有帮助：

1. 完整的 Controller / Service 代码；
2. 数据库表字段；
3. 期望业务流程；
4. 失败测试用例；
5. 具体异常日志；
6. 最终需要满足的 P4 测试要求。
