## 2. AI 助力分析（Q1：AI 最大的贡献是什么？）

### 2.1 核心贡献：消除模板化重复劳动

本阶段最大的收获是 **AI 完美承担了项目中模式化、重复性最高的代码编写工作**。

CampusHub 采用严格的模块分层架构（Entity → Mapper → Service接口 → ServiceImpl → Controller），三个新模块（message、match、admin）共需要 23 个 Java 文件，其中约 70% 遵循完全相同的代码模式。传统开发中，这些文件虽然技术含量不高但极其耗时（预计 8-10 小时），AI 在约 20 分钟内完成全部生成，且编译通过率 100%。

**估计节省时间：约 10 小时**

### 2.2 次要贡献：环境诊断能力

Claude Code 能够：
- 直接运行系统命令检测 MySQL 服务状态（`sc query MySQL80`）
- 检查已有数据库和表结构（`SHOW TABLES; DESCRIBE user;`）
- 直接执行 SQL 创建表和初始化数据
- 诊断 Git 推送失败原因（Connection reset → 切换 SSH）
- 运行 Maven 编译验证

这些"可以动手而不仅是动嘴"的能力大幅降低了"AI 说了一堆但我不知道怎么操作"的落差。

### 2.3 辅助贡献：Plan Mode 降低返工风险

在开始编码前，AI 主动进入"计划模式"，输出了包含 24 个文件的清单、API 接口表、数据库 ER 设计、依赖关系分析的完整计划。人工审核时及时发现了"拓展模块"的范围界定问题（需要在消息之外还包含智能匹配和后台管理），避免了返工。

## 3. AI 误导分析（Q2：AI 在哪些地方产生了误导？）

### 问题 1：前端设计"重新发明轮子"

- **问题描述**：AI 第一次生成前端页面时，完全替换了团队原有的 HTML 文件，从简洁的卡片式风格变为功能密集的紧凑型设计
- **发现方式**：用户直观感受"之前那个页面比这个美观一些"
- **根因分析**：AI 接收的隐式信号是"完成功能"，而非"在现有设计上增量扩展"。AI 没有"设计一致性"的审美概念
- **修正方案**：从 Git 历史取回原版 HTML，仅增加顶部模块导航标签，原版 CSS 和布局一字未改
- **教训**：前端任务必须显式声明"这是增量开发，保留现有设计系统"

### 问题 2：SQL 编码环境不匹配

- **问题描述**：生成的中文 INSERT 语句执行时报 `Data too long for column`
- **发现方式**：在 MySQL 中实际执行 SQL 文件时暴露
- **根因分析**：SQL 文件是 UTF-8 编码，但 MySQL 客户端默认连接字符集不一致，导致中文字符长度计算错误
- **修正方案**：添加 `--default-character-set=utf8mb4` 参数
- **教训**：任何涉及数据库、网络、文件系统的输出，都必须在目标环境中实际执行验证

### 问题 3：Git 操作权限假设

- **问题描述**：AI 最初建议使用 HTTPS + Token 方式推送，实际上用户的 Token 已过期
- **发现方式**：实际推送时遇到 403 错误
- **修正方案**：用户已有 SSH Key，切换为 `git@github.com` 的 SSH 方式后正常工作
- **教训**：AI 无法感知用户的认证配置状态，涉及远程操作时应先探测再决策

## 4. Prompt 改进计划（Q3：下一阶段如何改进？）

### 4.1 本阶段的提示策略反思

本阶段主要采用"目标描述型"Prompt（如"在现有代码结构上加上消息和拓展模块"），AI 自行完成了需求解析、模式识别、计划输出和代码生成。这种"开放式指令"在模式化开发中效率极高，但在涉及设计和环境的部分产生了偏差。

### 4.2 改进方向

| 策略问题 | 具体表现 | 改进措施 |
|----------|----------|----------|
| 缺乏"设计约束"声明 | AI 重写了前端样式 | 明确声明："只做增量扩展，不修改现有 CSS 和布局" |
| 缺乏"环境上下文"说明 | SQL 编码问题 | 在 Prompt 中补充运行环境信息（MySQL 版本、字符集、操作系统） |
| 缺乏"验收标准" | 前端风格差异 | 提前声明："生成后截图对比原版，差异不应超过 20%" |

### 4.3 推荐 Prompt 模板（面向后续阶段）

```
任务：{描述需要完成的功能}
约束：
1. 在现有代码库上增量开发，不修改已有文件的非必要部分
2. 遵循项目现有的 {分层模式/命名规范/代码风格}
3. 运行环境：{Windows 11, MySQL 8.0, JDK 17, utf8mb4}
4. 前端：保留现有设计系统，仅增加功能入口
验收：mvn compile 通过 + 实际数据库执行验证
```

## 5. 本阶段的核心工程决策

### 决策 1：匹配引擎的 MVP 策略

- **决策内容**：智能匹配模块暂不依赖 Demand（需求）和 Order（订单）模块，采用"用户-用户"直接匹配模型，通过 `userId → targetUserId` 建立匹配关系
- **AI 原始建议**：设计完整的 MatchRule + MatchResult + RuleEngine，预留 `demand_id` 和 `order_id` 字段
- **人工决策理由**：Demand 和 Order 模块尚未由其他组员完成，如果强依赖则模块无法独立开发和测试。当前实现中 `order_id` 设为可空，后续 Demand 模块就绪后只需加字段，无需改核心逻辑
- **后续影响**：正影响是当前即可独立演示匹配功能；负影响是后续需要一个小型迁移

### 决策 2：消息模块的会话模型中 user1_id ≤ user2_id

- **决策内容**：Conversation 表中始终保证 `user1_id < user2_id`，避免 (1,2) 和 (2,1) 产生重复会话
- **AI 原始建议**：在 SQL 层面通过唯一索引 `UNIQUE(user1_id, user2_id, order_id)` 防重
- **人工决策理由**：MySQL 的 UNIQUE 约束无法区分 (1,2) 和 (2,1)，需要在业务层做规范化。采用 `Math.min/max` 在 insert 时保证顺序
- **后续影响**：正影响是查询会话时只需 `WHERE user1_id=? OR user2_id=?`，无需双向查询

### 决策 3：后台管理权限校验方式

- **决策内容**：管理员权限在 Controller 层通过 `checkAdmin(token)` 方法校验，而非通过 Spring Security 的 `@PreAuthorize` 注解
- **AI 原始建议**：使用 JwtInterceptor + 自定义注解
- **人工决策理由**：项目当前未引入 Spring Security 的完整体系，使用简单方法校验与现有代码风格一致，避免引入额外复杂度
- **后续影响**：快速可用，但若后续权限系统复杂化，需要重构为注解方式

## 6. 协作模式总结

### 6.1 本阶段的人机分工

```
人类（康乔其）                    AI（Claude Code）
─────────────────────────────────────────────────
• 明确需求范围                    • 自动探索代码库
  "拓展包括智能匹配和后台管理"       → 识别分层模式和命名规范
• 纠正设计偏差                    • 输出实现计划
  "不能改原来的页面设计"            → 24 个新文件的清单和依赖分析
• 批准/拒绝执行                   • 生成全部代码
  → Plan Mode 审核通过             → 23 Java 文件 + SQL + HTML
• 验收测试                        • 执行环境操作
  → 启动应用、测试接口              → Maven 编译、MySQL 建表、Git 推送
```

### 6.2 关键发现

1. **"先计划后执行"模式显著优于"边问边做"**：Plan Mode 让人类在代码生成前就能评审架构设计，避免了约 70% 的返工
2. **AI 的操作能力（执行命令）是信任度的关键加分项**：如果 AI 只能"建议"如何建表而需要人类手动操作，效率提升会大打折扣
3. **AI 对"美感"和"设计一致性"没有概念**：前端任务需要更严格的约束声明
4. **增量开发 > 全量替换**：AI 应被引导为"在现有代码上做最小侵入性修改"，而非"重写这个文件"

### 6.3 对比团队前期 AI 使用经验

| 维度 | P1 阶段（需求分析） | P4 阶段（代码开发） |
|------|---------------------|---------------------|
| AI 角色 | 灵感生成器 | 编码协作伙伴 |
| 交互模式 | 单轮问答 | 多轮对话 + 操作执行 |
| 输出可控性 | 低（需大幅改写） | 中高（模板代码直接可用） |
| 关键风险 | AI 可能误解业务场景 | AI 可能破坏现有设计 |
| 成熟度 | 实验/探索 | 可流程化使用 |

## 7. 对后续阶段的建议

1. **固化"Plan → Generate → Verify → Fix"四步流程**，将其作为每次 AI 辅助开发的标准操作程序
2. **前端任务必须加"设计约束"前缀**，防止 AI 重新设计 UI
3. **建立"AI 代码审查清单"**：Entity/DTO 可跳过审查，Service/Controller 须人工过目，SQL 须在目标库执行验证
4. **利用 Claude Code 的环境操作能力**，不只是让 AI 生成代码，也让 AI 去执行编译、测试、数据库操作
