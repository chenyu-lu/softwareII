# Phase 2：架构决策记录 (ADR) — 二元一次方程组

本文件详细记录了“校园互助平台”在体系结构设计阶段的关键决策。每条决策均包含 AI 建议与人工根据项目实际情况（10周开发周期、单服务器部署）进行的修订对比。

---

## ADR-001：采用模块化单体架构 (Modular Monolith)

### 状态
已接受

### 背景
项目需要在 10 周内交付，且部署方式已确定为单服务器 Docker 容器化。虽然系统包含用户中心、匹配引擎等多个业务模块，但团队规模较小（4人），需优先降低运维与开发复杂度。

### 决策
我们决定不采用微服务，而是采用**模块化单体架构**。各业务模块在代码层面通过包结构进行逻辑隔离，但在运行层面处于同一 SpringBoot 进程中，模块间交互通过本地 Spring Bean 注入 Service 接口实现。

### 理由
1. **可行性**：避免了微服务带来的分布式事务、服务发现和远程调用（RPC）的复杂性，确保在 5 月 3 日前完成设计。
2. **性能优化**：本地方法调用延迟远低于网络请求，更适合单服务器的部署环境。
3. **团队统一性**：符合队友在任务 2 中提出的“不拆分微服务、同进程内本地方法调用”的技术共识。

### 后果
- **正面影响**：极大地简化了 CI/CD 流水线和本地调试过程。
- **负面影响**：模块间存在代码级耦合，未来若需独立扩展特定模块需重构。
- **风险**：需严格执行包管理规范，防止模块间出现循环依赖。

### AI 辅助记录
- **AI 初稿内容摘要**：推荐使用 Spring Cloud 微服务架构以应对校园高并发场景。
- **人工修订内容**：改为模块化单体架构，并明确通过 Service 接口进行本地调用。
- **修订理由**：AI 忽略了学生项目的人力瓶颈与部署成本；微服务会导致项目在环境搭建阶段就耗尽工时，不符合可行性原则。

## ADR-002：利用 Redis 实现智能匹配缓存与接口限流

### 状态
已接受

### 背景
“智能匹配引擎模块”涉及用户标签、位置及信用分等多维度复杂计算，计算开销较大。同时，系统需在基础支撑模块中实现接口限流，以防止恶意抢单或暴力登录。

### 决策
我们决定引入 **Redis** 作为核心中间件，不仅用于存储匹配引擎的计算结果缓存，还用于管理用户登录的 JWT 令牌以及实现全局接口限流计数器。

### 理由
1. **提升体验**：将匹配结果缓存至 Redis，可使任务列表刷新响应达到毫秒级。
2. **多功能复用**：单个中间件同时解决缓存、Session 管理和限流问题，符合技术选型中的“轻量高性能”要求。

### 后果
- **正面影响**：显著降低了 MySQL 在高频筛选任务时的读写压力。
- **负面影响**：增加了系统对外部组件的依赖。

### AI 辅助记录
- **AI 初稿内容摘要**：建议使用本地缓存（如 Caffeine）以进一步减少架构层级。
- **人工修订内容**：坚持使用 Redis，并将其职责扩展至限流和消息临时存储。
- **修订理由**：考虑到未来可能的分布式部署需求，Redis 比纯本地缓存更具备前瞻性，且能更好配合 Docker 容器化部署。

## ADR-003：基于本地事件驱动的信用分更新策略

### 状态
已接受

### 背景
“评价与投诉模块”在订单完成后，需要同步更新“用户中心模块”中的用户信用分。在单体架构下，需确保数据同步的实时性与一致性。

### 决策
我们决定不引入复杂的外部消息队列（MQ），而是采用 **Spring 本地 Service 调用**。当评价归档后，直接调用用户中心模块提供的 `updateCreditScore` 接口。

### 理由
1. **原子性保证**：在同一数据库事务中，通过本地调用可确保“评价提交”与“分数更新”同时成功或回滚，保证了信用体系的严谨性。
2. **架构一致性**：符合队友定义的“模块间不使用 MQ 远程调用”的开发原则。

### 后果
- **正面影响**：开发逻辑简单，调试成本低，能快速响应 5 月 3 日的提交需求。
- **负面影响**：增加了模块间的逻辑耦合。

### AI 辅助记录
- **AI 初稿内容摘要**：推荐使用 RabbitMQ 或 Kafka 实现评价与信用分模块的解耦。
- **人工修订内容**：改为直接 Service 注入调用。
- **修订理由**：在单服务器单体应用中，引入 MQ 会增加消息丢失风险和系统复杂度，属于“过度设计”，不利于项目的快速落地。
