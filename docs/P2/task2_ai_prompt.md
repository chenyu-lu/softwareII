一、整体架构与模块依赖关系
核心依赖规则

    基础支撑模块：所有模块的公共依赖（全局配置、认证、工具、异常）
    用户中心模块：订单、匹配、交易、评价、后台管理的基础用户数据依赖
    需求订单模块：匹配引擎、消息通知、评价投诉的核心业务依赖
    匹配引擎模块：仅依赖用户中心（标签 / 信用分）、需求订单（需求数据）
    二手交易模块：依赖用户中心、消息通知、评价投诉
    评价投诉模块：依赖用户中心（信用分）、订单 / 交易模块
    消息通知模块：全模块通用通知依赖
    后台管理模块：依赖所有业务模块的数据查询接口

三、模块间调用规范（必守规则）
1. 通信协议

    统一使用 HTTP/HTTPS + RESTful 接口
    统一返回格式：
    {
    "code": 200,
    "msg": "操作成功",
    "data": {},
    "requestId": "唯一请求 ID"
    }

2. 调用权限控制

    所有跨模块调用必须携带Token，由基础支撑模块统一校验
    敏感接口（信用分修改、内容审核）增加签名校验
    禁止跨模块直接操作数据库，必须通过接口调用

3. 异常处理机制

    所有模块调用异常，统一调用基础支撑模块的异常处理接口
    超时重试：核心接口（订单状态、信用分）支持 3 次重试
    熔断降级：调用失败时返回默认值，不阻塞主流程

四、核心业务流程接口调用示例
示例 1：需求发布 → 智能匹配 → 订单生成

    需求订单模块调用用户中心：校验用户认证 + 信用分
    需求订单模块调用基础支撑：校验发布配置
    需求订单模块调用匹配引擎：触发智能匹配
    匹配引擎调用用户中心：获取用户标签 + 信用分
    匹配完成后，需求订单模块生成订单
    需求订单模块调用消息通知：推送匹配成功消息

示例 2：评价完成 → 信用分更新

    评价投诉模块创建评价
    评价投诉模块调用用户中心：更新用户信用分
    用户中心同步信用分结果
    评价投诉模块调用消息通知：推送评价结果

五、接口管理建议

    使用 Knife4j/Swagger 生成在线接口文档，模块间共享
    接口版本控制：/api/v1/xxx，兼容迭代更新
    统一日志追踪：通过requestId串联全模块调用日志

    这套接口设计完全解耦 8 大模块，每个模块只暴露核心能力接口
    基础支撑 + 用户中心作为底层底座，支撑所有上层业务
    接口规范统一、调用关系清晰，可直接用于前后端开发、微服务部署

问题2：对这些模块要确定技术栈，请问哪种部署方式可以低成本，符合校园项目要求
先给结论：最优低成本方案 = SpringBoot 单体多模块 + 内置 Tomcat + 单机部署 + MySQL 单库，完全满足校园项目、开发简单、部署零成本、学习成本低、适配你所有业务模块；不推荐微服务、不推荐 Docker 集群、不推荐云服务器高配。
一、先定校园项目核心约束

    低成本：尽量免费 / 零服务器费用、不用花钱买中间件、不用注册微服务注册中心、不用 Redis 集群、不用 MQ 付费版；
    易开发易部署：学生团队维护、人手少、不用运维；
    适配 8 大模块：基础支撑、用户中心、订单、匹配引擎、二手交易、评价投诉、消息通知、后台管理；
    访问量小：校园内部使用，并发低、数据量小，不需要分布式、扩容、高可用。

二、推荐最终技术栈（校园版 极简低成本）
后端技术栈

    核心框架：SpringBoot 2.7.x / 3.2.x
    项目结构：SpringBoot 多模块单体项目（把你 8 个业务模块拆成子 Module，代码解耦但部署还是一个包）
    ORM：MyBatis / MyBatis-Plus
    数据库：MySQL 8.0（本地 / 校园虚拟机 / 学生免费云数据库均可）
    认证授权：SpringSecurity + JWT（基础支撑模块直接集成）
    接口文档：Knife4j/Swagger
    工具类：Hutool、Lombok
    消息通知：不用 MQ，直接内存异步 + 定时任务搞定（校园体量完全够用，省掉 RabbitMQ/RocketMQ 部署成本）
    匹配引擎：直接写 Java 内存规则引擎（标签 + 位置 + 信用分 规则代码化，不用大数据框架）

前端技术栈（低成本标配）

    管理后台：Vue2/Vue3 + Element Plus
    用户端：Vue/H5 即可，不用小程序原生，降低开发量

部署中间件 全部极简省钱版

    缓存：不用独立 Redis，先用本地 Caffeine 本地缓存，后续量大再单独装 Redis 单机即可
    消息队列：不部署 MQ，用 Spring 异步线程池 + 定时任务轮询
    网关、注册中心、配置中心：全部不用（单体多模块不需要）

三、部署方式选型对比（只选最适合校园的）
方案 1：SpringBoot 单体多模块部署【首推 ✅ 最优】
架构结构
一个父工程，下分 8 个子模块：campus-platform├─ base-support 基础支撑├─ user-center 用户中心├─ demand-order 需求订单├─ match-engine 匹配引擎├─ second-hand 二手交易├─ evaluate-complaint 评价投诉├─ message-notice 消息通知└─ admin-manager 后台管理
所有模块打包成一个 jar 包，java -jar 直接运行。
优点

    成本最低：只需一台低配机器甚至个人电脑、校园虚拟机、学生免费云服务器（1 核 2G 足够）；
    开发简单：模块间直接本地方法调用，不用写 HTTP 接口跨服务调用，不用处理熔断、注册、网关；
    部署极简：只部署一个 jar，不用运维、不用拆分服务；
    适配校园项目：并发低、业务不复杂、学生团队能 hold 住；
    后期想拆微服务，子模块可以直接无缝拆分，架构预留扩展性。

缺点
后期超大并发才会有瓶颈，校园项目永远遇不到。
方案 2：前后端分离 + 单体部署（配合方案 1）
前端打包 dist 扔 Nginx，后端一个 Jar，Nginx 反向代理，最简单上线方式，零成本。
方案 3：微服务部署（不推荐 ❌ 校园项目没必要）
SpringCloud + Nacos + Gateway + 每个模块单独服务

    缺点：架构复杂、要部署注册中心、网关、每个模块单独打包部署、运维成本高、学习成本大、完全多余，校园小并发纯属过度设计。

方案 4：Docker Compose 单机容器化（可选进阶）
在方案 1 基础上，把 MySQL、后端 Jar、Nginx 打成 Docker 容器，单机 Docker Compose 一键启动。

    适合：想练容器技术，但还是单体多模块架构，不拆微服务；
    成本依旧极低，一台机器就能跑。

四、模块间调用方式（适配低成本单体架构）

    开发阶段：8 个模块在同一个 SpringBoot 工程里，直接依赖注入调用方法，不用 HTTP 接口、不用 Feign、不用跨服务通信；
    接口预留：按你之前设计的 RESTful 接口写 Controller，既支持内部调用，也支持前端 / 第三方调用；
    后续如果业务变大，直接把某个子模块拆成独立微服务，接口不用改，平滑迁移。

五、最低成本部署硬件 / 环境选择

    首选：学生免费云服务器（阿里云 / 腾讯云学生机 1 核 2G 免费 / 低价）
    备选：实验室闲置 Linux 主机、自己电脑长期开机、校园虚拟机
    环境：只装 JDK1.8/17 + MySQL8.0 + Nginx 三样，无其他额外中间件。

六、最终落地建议（直接照着搭）

    用 IDEA SpringBoot 多模块工程，按你 8 个模块拆子 Module；
    技术栈固定：SpringBoot + MyBatis-Plus + MySQL + JWT + Vue；
    部署方式：单体 Jar 单机部署，不搞微服务、不搞复杂中间件；
    消息、匹配、缓存全部业务代码内置实现，不额外部署中间件，极致低成本；
    模块间内部直接调用，对外暴露 REST 接口，兼顾开发简单和架构规范。
